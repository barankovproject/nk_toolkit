# Known problem canals — Ditches (`ditch_03_build_long`, `ditch_04_build_cross`)

Split out of `docs/process/03_testing.md` (2026-09-04) — see that file for the shared
testing rules/conventions this table follows.

| Canal | Issue found | Fixed in commit |
|---|---|---|
| НК-1А / НК-1E (cross ditches, e.g. sta 179 / 331 / 3527) | `build_cross_ditches` solver oriented some ditches start-below-end: the θ search kept the smallest skew with `abs(za − zb)` in band, accepting solutions where the cut (start) bank came out **LOWER** than the fill (end) bank — a ditch draining uphill with the гаситель on the high side. Confirmed by re-solving stored stations (`debug/ditch_solver_check`). Fix in `ditch_solver.solve_ditch`: keep only skews with `z_cut > z_fill` (signed grade, drains start→end) and fall back to the **opposite** rotation direction when the aimed one never lifts the cut above the fill; the plan-PI neighbour-consistency pass (`ditch_04_build_cross.builder`) now ignores neighbours farther than `CONFIG.neighbour_max_dist` (50 m). Verified: re-solving 35 ditches on 1а/1e → 35/35 start>end, 0 inverted, 0 skipped. | uncommitted |
| НК-1E (cross ditch #11, sta 624.194) | `ditch_04_build_cross` drew a runaway connector (L2D 43.89 m vs ~31 m hand-drawn): the fill end is **not a real бровка** — the cross-profile ran into the surface edge (`break_point` → `"edge"`, `end_scarp=none`, status `no_bank`), so `build_killer`'s подошва (`_surface_foot`, = the TIN boundary at the toe) sits right at the бровка (`s_foot ≈ s_br`, `z_foot ≈ z_br_surf`), `g_scarp` degenerates, and the near-horizontal connector meets the descending (buried) ditch line via `line_intersect_s` far out. Fix in `build_killer`: still build the гаситель apron where the toe is, but **reject the connector when its `connector_top` falls outside the откос span `[s_top, s_foot]`** (runaway) and instead join the main ditch straight to the apron `near` (`has_connector=False`, `connector_top == near`) when that direct run still drains at `0 < slope ≤ slope_max`; a real, tall откос keeps the connector. Both builders skip drawing the connector polyline when `has_connector` is False. **Separately**: when **both** banks are откос выемки (`scarp_start > 0` and `scarp_end > 0`) the ditch is entirely in a cut — no насыпь — so no гаситель/connector is built at all (guarded in both builders before `build_killer`). | uncommitted |
| НК-1А then НК-1E (cross + long ditches, same drawing) | The `Canal` property set value was overwritten for **all** ditches with the single config `CANAL`: the build step (`ditch_04_build_cross.builder`, `ditch_03_build_long.builder`) wrote every ditch onto the bare base layer (`inf_md_ditch` / `inf_ct_toe`) and tagged `canal=CANAL`, while the refresh derives the canal from the layer **suffix** (`trasse_for_layer`). With no suffix, the refresh re-stamped every ditch with the current default (CANAL), so building 1а then 1e relabelled 1а's ditches as 1e. `ditch_03` was worse — it only processed the bare layer (ignoring `inf_ct_toe_<trasse>`) and flattened the 3D rebuild back onto the bare layer. Fix: the build now routes each run onto the canal's own suffixed layer — `inf_md_ditch_<CANAL>` (+ `_connector_`/`_killer_`, created by `ensure_md_layer`) for cross; for long it preserves the source polyline's own layer and derives `canal` from its suffix (`layer_for_trasse` is the inverse helper). Verify: build A, then B, refresh → each ditch's `Canal` = its own canal; re-running a canal adds no duplicates. | uncommitted |

## When to add a canal here

- Run on a new canal's cross/long ditches (`ditch_03_build_long`/`ditch_04_build_cross`), something breaks
- Add canal name + symptom before fixing
- After fix: add the commit reference
